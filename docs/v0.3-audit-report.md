# v0.3.0 implementation audit

**Scope:** two separate self-review passes over the admission-witness feature
branch based on `b97d9e2ff9fa32b62b42d86fba70de688d3b0416`.

## Pass 1 — semantic adversarial audit

The pass attempted four unsafe constructions required by the implementation
handoff.

| Attempt | Finding | Resolution |
|---|---|---|
| False local-repair claim | Core shape validation can reject empty, duplicate, wrong-scope, contradictory, or already-quoted requirements, but opaque state means it cannot prove a list is semantically complete. Earlier validator wording overstated this. | Prose and code comments now assign semantic completeness to the binding. A behavioral test injects a structurally valid but incomplete `COMPLETE` witness and proves the mandatory new quote/fresh evaluation finds the omitted unit and dispatches nothing. |
| Unauthorized added transition | A witness contains information, not authority. Core cannot safely invent a domain authorization protocol. | The retail binding exposes and tests its authorization boundary. The amended proposal is rejected when permission covers only the original delivery unit. Normative/security prose requires authorization before exposing sensitive witness data and again for the amended proposal. |
| Stale-state bypass | `evaluatedAt` or `stateRef` could be mistaken for a lock, and a witness could become stale before reuse. | Repair always creates a new proposal and quote. Tests mutate live state between refusal and re-quote and verify a fresh missing set; a separate snapshot-drift test refuses before dispatch. The distributed check-to-dispatch gap remains explicitly binding-owned. |
| False atomicity claim | Co-inclusion might be misread as atomic execution of all included units. | `REQUIRES_COINCLUSION` is defined only as admission. Tests show a companion unit can later be `REFUSED` by an acceptance constraint or `INDETERMINATE` and then reconciled, while complete per-unit coverage is preserved. Bindings needing all-or-nothing economics require a stronger execution guarantee. |

The pass also found that a binding hook with hidden mutation side effects could
invalidate the no-dispatch promise. The hook is now explicitly observational;
this remains a binding conformance/audit obligation because core cannot detect
hidden side effects.

## Pass 2 — schema/type/prose consistency audit

The pass compared the JSON Schema, TypeScript mirror, normative prose,
reference provider, retail binding, fixtures, and conformance documentation.

Findings and resolutions:

- The untouched v0.2.0 schema and TypeScript type allowed `APPLIED` without
  `committedEffects`, although normative prose required the array. v0.3.0 now
  uses a discriminated `UnitResult`, requires `committedEffects` even when
  empty, excludes outcome-inapplicable fields, and tests both schema and
  runtime rejection. This is a localized baseline consistency repair directly
  preserving effect coverage.
- The worked fixtures originally showed the refusal and amendment but not the
  surrounding request/result messages. They now show the original proposal,
  quote, commit request, refusal, amended proposal, new quote, second request,
  and complete successful per-unit result.
- All package versions are `0.3.0`; the normative schema identifier is
  `https://mutation-safety-envelope.org/schema/v0.3.0/mse-core.schema.json`.
  Current documentation reports 142 tests, while the historical v0.2.0 counts
  remain explicitly historical.
- New core source and relation semantics contain no retail operations or state
  vocabulary. Those remain in `examples/retail/admission-policy.ts`.
- The review response attributes the delivery gates to Weston as
  provider-reported semantics and labels every new response shape as proposed
  MSE design. It does not claim that a drafted reply was posted or that UCP
  accepted/adopted the design.

Checks used for this pass include parsing every repository JSON file, strict
draft-2020-12 schema compilation, TypeScript build, fixture conformance,
behavioral tests, `git diff --check`, version/count scans, and targeted scans
for domain vocabulary in changed core code.

## Remaining honest limits

- No external provider has validated semantic witness completeness.
- The reference provider demonstrates a synchronous in-process
  evaluation-before-dispatch boundary, not a distributed lock or transaction.
- Co-inclusion does not provide cross-unit atomicity.
- A separate delivery unit does not solve ownership of genuinely joint/shared
  effects such as tax allocated across units.
- Only concrete provider evidence should justify additional relation types.
