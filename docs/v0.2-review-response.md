# v0.2.0 review response: what UCP Discussion #799 falsified, and what changed

> **Historical revision record.** v0.3.0 later addresses dependent
> admission, stable relation declarations, and live repair witnesses. This
> document is preserved as the v0.2.0 record; see
> [`/docs/v0.3-review-response.md`](./v0.3-review-response.md) for current
> changes rather than reading "remains unresolved" below as current status.

**Status:** Experimental / External Review Candidate. This document
records an evidence-driven revision to MSE's core, made in direct response
to external technical criticism. **It is not a claim of UCP adoption or
endorsement of MSE** — see [`/docs/DISCLAIMER.md`](./DISCLAIMER.md), which
still fully applies. UCP maintainers and the wider UCP Discussions
community raised the issues below; they did not adopt, bless, or co-author
MSE by doing so, and nothing in this document should be read to imply
otherwise.

## What external review falsified

MSE v0.1.0 modeled commit determinacy as a single mutation-wide field:

```text
CommitResult.outcome: "APPLIED" | "REFUSED" | "INDETERMINATE"
```

External review in UCP Discussion #799 identified two substantive problems
with this shape, both accepted here as successful falsifications of a
v0.1.0 design assumption — not defended or rationalized away:

1. **A single mutation attempt can span multiple independently committing
   units.** A request modifying several parts of a commercial resource at
   once — several order lines, several travel segments, several contract
   clauses — can legitimately result in one part applying while another is
   refused, and a third left indeterminate, *in the same commit attempt*.
   v0.1.0's single scalar `outcome` could not represent this: any attempt
   to report it would have had to arbitrarily pick one part's outcome to
   represent the whole, discarding real information about which parts
   actually committed.
2. **`INDETERMINATE` had no normative resolution path.** v0.1.0 correctly
   said a caller must not blindly retry an `INDETERMINATE` commit, but
   said nothing about how the caller *could* safely resolve the
   uncertainty. The v0.1.0 reference implementation happened to expose a
   `reconcileIndeterminateCommit()` helper, but this was implementation
   convenience, not a normative contract — nothing in the schema
   represented it, so a different implementation had no obligation to
   offer anything equivalent, and a caller reading only the schema had no
   way to know a resolution path could exist at all.

Both findings are treated as valid critiques of the v0.1.0 core, not
edge cases to special-case around the existing shape. See
[`/spec/normative-spec.md`](../spec/normative-spec.md) §1a-§1c for the
full account of finding 1, and §4b-§4c for finding 2.

## What changed

A single-paragraph summary; see the normative spec for the actual
requirements, and [`/schema/mse-core.schema.json`](../schema/mse-core.schema.json)
for the exact shapes.

- **`CommittingUnit`** is new: a domain-blind representation of one
  independently committing unit, carrying an opaque `unitRef` and its own
  `effects`. `MutationQuote.units: CommittingUnit[]` replaces v0.1.0's
  top-level `effects` array. The set of units is fixed no later than quote
  time, so a caller can check result coverage against a set it saw before
  committing.
- **`CommitResult.unitResults: UnitResult[]`** replaces the v0.1.0
  mutation-wide `outcome`/`refusalReason`/`committedEffects` triple
  entirely. One `UnitResult` per `CommittingUnit`, no silent omission
  (enforced both normatively and by
  [`assertCommitResultCoversAllUnits`](../src/core/validate.ts)).
- **`CommitResult.aggregateHint`** is new and explicitly
  **non-authoritative** — a derived convenience summary
  (`ALL_APPLIED`/`ALL_REFUSED`/`ALL_INDETERMINATE`/`MIXED`) that a caller
  MUST NOT use as a substitute for inspecting `unitResults`.
- **`Reconciliation`** is new, required on every `INDETERMINATE`
  `UnitResult`: a `mode` (`MACHINE_RESOLVABLE` / `AUTHORITATIVE_READ` /
  `NONE`) plus a `correlationId` when a real path exists. A binding
  exposing a machine-resolvable or authoritative-read path MUST document
  how it's invoked, how it correlates back to the original attempt, how
  its result maps to the same unit, and — critically — that it resolves
  the prior attempt rather than replaying the mutation. The reference
  implementation's `ReferenceProvider.reconcile()` demonstrates this: it
  looks up what actually happened via an injected fault-simulation hook,
  and can resolve to `APPLIED`, `REFUSED`, or remain unresolved — it is
  deliberately not hardcoded to always confirm success, because a
  reconciliation path that could only ever report success would not be a
  real reconciliation path.
- **`Effect.effectId`** is new and required: an opaque identifier unique
  within a quote across all units. Once multiple units can exist, `type`
  alone is no longer sufficient to correlate an effect across
  quote/commit/receipt (two units can legitimately produce same-typed
  effects), so all correlation (`AcceptanceConstraint`, receipt entries)
  now runs over `effectId`.
- **`Receipt.mutationOutcome`** is removed entirely. Commit-unit
  determinacy lives only in `CommitResult.unitResults`; re-introducing any
  outcome summary on `Receipt` would recreate the exact
  information-collapsing problem finding 1 identified, just one hop
  downstream.

None of this adds domain vocabulary to the core. No SKU, fare, plan,
billing period, or refund concept was introduced; `unitRef` and
`effectId` are as domain-blind as `Effect.type` always was. This is a
structural fix to how commit determinacy and effect identity are
represented, not an expansion of what MSE claims to model.

### Follow-up hardening: correlation-chain ownership (same revision)

A manual review of this revision's own diff (before this branch was
pushed) found that adding `effectId` established that an effect could be
identified, but not that it was correctly *attributed* — the original
`assertReceiptCoversAllCommittedEffects` established coverage primarily by
`effectId` presence, which meant a receipt could carry a valid, genuinely
committed `effectId` under the wrong `unitRef` and still pass. Two things
were added to close this, still within v0.2.0 (no version change, no
protocol redesign; see spec §7b for the full normative text):

- `assertCommittedEffectsBelongToUnits` — validates that a
  `UnitResult`'s `committedEffects` only ever claims effects actually
  quoted under that same unit, and that no effect is claimed by more than
  one unit. Deliberately a separate check from EXACT-guarantee honoring,
  since a value-drift check alone cannot catch a correctly-valued but
  misattributed effect.
- A strengthened `assertReceiptCoversAllCommittedEffects` that now checks
  `effectId` **and** `unitRef` agreement per receipt entry (not effectId
  presence alone), rejects unknown/uncommitted `effectId`s, and rejects
  duplicate receipt entries for one `effectId`.

`ReferenceProvider` itself was not changed structurally by this
follow-up (it always attributes committed effects to the unit it copied
them from, so it could not violate this on its own) — the new validators
exist to check ownership when it is not otherwise guaranteed by
construction, e.g. by a `DriftSimulator` override or a different
implementation entirely.

## What remains unresolved

Carried over or newly surfaced by this revision — see
[`/spec/normative-spec.md`](../spec/normative-spec.md) §8 for the full,
current list, and [`/docs/ambiguities.md`](./ambiguities.md) for the
broader history:

1. Multiple outstanding quotes against the same target (unchanged from
   v0.1.0, still open).
2. Whether `commitConsistency`/`snapshot` should be expressible per-unit
   rather than only per-quote, now that a quote can have multiple
   independently committing units with potentially different consistency
   needs.
3. **Cross-unit/shared effects.** v0.2.0's model assumes every effect
   belongs to exactly one unit. It has no representation for an effect
   that is a genuine joint consequence of more than one unit (e.g. one
   combined tax recalculation resulting from edits to two order lines at
   once). This is flagged explicitly rather than resolved by guessing,
   because either obvious option — arbitrarily assigning it to one unit,
   or duplicating it across units under different `effectId`s —
   misrepresents something real, and resolving it without a real
   cross-unit-effect example from an actual provider risks guessing wrong
   in a way that's expensive to walk back later.
4. Whether `aggregateHint`'s four-value vocabulary is the right level of
   detail for a field whose entire design goal is to stay minimal and
   clearly secondary to `unitResults`.

## Evidence and falsification posture, updated

This revision does not change the posture set out in
[`/docs/falsification-notes.md`](./falsification-notes.md): all validation
of the *new* per-unit and reconciliation shapes is, again, self-consistency
— schema, reference implementation, and fixtures updated together by the
same process that designed them, now additionally informed by one round
of real external technical criticism. That is meaningfully more evidence
than v0.1.0 had, but it is still not independent, adversarial, or
production validation. The next meaningful test of this revision is
further external review of the same kind that produced it — including,
plausibly, further falsification of the shapes introduced here (see
"What remains unresolved" above for the most likely candidates).
